---
description: Run a task end-to-end through the full agentic loop — plan, implement, verify, review (code + security + UX), resolve, report.
argument-hint: [task description]
---

Execute the task: **$ARGUMENTS**

Run the full Claude Agentic Stack loop (see MANUAL.md). **Do not skip the review gate.**

Execution model: you **edit on the host**, but **all builds/tests/installs run on the sandbox VM** over SSH (`/cas:verify` syncs the tree and runs them there). Never run build/test on the limited host.

1. **Understand & plan.** In this order:
   1. **Provenance guard** — before reading or writing any state: if `git ls-files .agentic` returns anything, stop and report — tracked run state is never trusted (the same guard as `/cas:resume`).
   2. **Stranded-run check** — existing `.agentic/` state counts as *unfinished* unless it passes the **done test** below. On a stranded run, stop and surface it — offer `/cas:resume` or get explicit confirmation to discard; in a headless run this is a hard failure (report and stop, never auto-discard) — rather than silently overwriting a resumable run.
   3. **Restate** the goal and acceptance criteria — and, when the request **literally names** several deliverables ("do R4, R5 and R6", a numbered list), the queue itself, item by item; never split a single request into deliverables of your own (headless: record the enumeration in `task.md` as an assumption and repeat it in the final report).
   4. **Persist the task**: write `.agentic/task.md` (creating `.agentic/.gitignore` containing `*` first if absent — MANUAL.md → *Run artifacts*) with the task, the acceptance criteria, a `Base: <git rev-parse HEAD>` line, a `Status:` line (`planning | designing | implementing | verifying | reviewing | resolving | blocked | done`), and a `- [ ]` checklist — when the task names several deliverables, one box per **deliverable** under an `Accepted scope:` heading, in the order the request gave them — redacting secret-looking strings from the task text per MANUAL.md → *Run artifacts*. This is the run's durable target — keep it live: check items off as they complete and update `Status:` at each phase transition (the checklist tracks the deliverable queue and the current item's plan steps; `Status:` tracks where the loop is, so `/cas:resume` re-enters at the right phase rather than mistaking "implemented" for "done"). Never skip the file when the request names more than one deliverable; otherwise skip it only for a trivial one-file change.
   5. **Plan** — for anything beyond a trivial one-file change (a queue item that is itself trivial skips the planner, not the file), dispatch the `cas:planner` agent — scoped to the **current deliverable** when there is a queue, and, once earlier items are checked, given what they committed (`git log <Base>..HEAD`) so the item is planned against the code as it now stands (the reconcile) — to produce an ordered plan, the files to touch, a test strategy, risks, and a **Surface impact** line (a new screen / endpoint / command / schema / public API change — or `none`). Use the `Explore` agent for broad search so your context stays clean. Nest the plan steps (and the item's `Surface:` / `Design:` lines) under the current item's box (MANUAL.md → *Scope & the queue*).

   **The done test** (also applied by `/cas:resume` and `/cas:prototype`): state is *verifiably done* when it holds a final `DONE` prototype checkpoint whose recorded commit(s) `git log` confirms, or a `task.md` at `Status: done` whose every box is checked **and confirmed**. A checked box is confirmed when it is marked `skipped by user` or `kept by user`, or its recorded SHA (`- [x] <deliverable> — <sha>`, or a flat run's `Commit: <sha>` line) is in `git rev-list --first-parent <Base>..HEAD` (the run's own commits, not ones a merge brought in) and no other box records the same SHA. After a `/cas:ship` squash, a `Shipped: <new> squashes <old tip>` line confirms the committed boxes instead — but only when `<new>` is in `<Base>..HEAD`, `<old tip>` is the latest SHA-bearing box, every box SHA is in `<Base>..<old tip>`, and `<new>` and `<old tip>` have the same tree (`git rev-parse <sha>^{tree}`); if the old objects are gone, surface it for the user to confirm, and whenever the test relies on `Shipped:`, say "shipped as <new> per `/cas:ship`". A checked box that meets none of these is an unverified claim, and any disagreement between `Status:` and the boxes means unfinished; a `task.md` with no `Base:` line predates this format — surface it as old-format state, not as an unverified claim.

2. **Design checkpoint (conditional).** If `cas:planner` reported a Surface impact other than `none` — or `$ARGUMENTS` carries `design=ask` / `design=auto` — record `Surface: <the listed surfaces>` in `task.md`, set `Status: designing`, and run `/cas:mockup <surface> design=<mode> fidelity=wireframe` — once per medium, covering every listed surface of that medium (mode defaults to `ask`; a headless run takes `auto`; pass `fidelity=styled` only when the task asks for a visual direction — a precision change to an existing app follows its design system). `design=skip`, or a Surface impact of `none`, skips it: a change *to* an existing surface never triggers variants. Record the outcome in `task.md` as one `Design: <MOCKUP verdict> — .agentic/design.md#<surface>` line per `/cas:mockup` call (or `Design: skipped — <reason>`); a `DEFAULTED` pick is an assumption — say so there and in the final report.

3. **Implement.** Make the smallest viable change, reusing existing code and matching conventions. When `.agentic/design.md` covers the surface, build **to** it: a minor deviation is recorded in `task.md` as an assumption with its reason; a must-preserve item you cannot meet is an ASK, never a silent change. Resolve any open question from the plan first — ask the user only if it is a genuine ambiguity per MANUAL.md's autonomy policy. If the sandbox VM isn't already warm, first kick off a one-time **background** sync + dependency install on it (MANUAL.md → *Where things run* → *Warm the sandbox early*) so the cold install finishes while you edit and `/cas:verify`'s install is a no-op.

4. **Verify.** Run `/cas:verify` and drive build + lint/type-check + tests **and the runtime smoke** to green. For non-trivial unit coverage dispatch the `cas:test-engineer` agent (give it `.agentic/design.md` when present — approved examples become tests); for a runnable app, `/cas:verify` boots and drives it via `cas:e2e-tester`. On a green pass, record in `.agentic/task.md` the commit SHA at that verify and whether the worktree was clean — the checkable evidence `/cas:resume` needs to skip a redundant re-verify.

5. **Review gate (mandatory).** In a single message, dispatch `cas:code-reviewer` and `cas:security-reviewer` in parallel on the current diff — and `cas:ux-reviewer` too if the change touches UI (give it the task/spec and `.agentic/design.md` when present; it reads the screenshots from verify under `.agentic/screenshots/standalone/` and the mockups under `.agentic/design/`). Give each: the `git diff`, the task description, `.agentic/design.md` when present (every reviewer checks fidelity to it for its own dimension), and pointers to the relevant files (they start with a clean context and cannot see this conversation).

6. **Resolve.** Fix every Critical and High finding, plus reasonable Mediums. Re-run `/cas:verify`. Re-dispatch the reviewer for any dimension whose code you changed (`cas:security-reviewer` for security-relevant fixes, `cas:ux-reviewer` for UI fixes). Repeat until every dispatched reviewer reports `GATE: PASS`. If a failure won't resolve, apply the circuit-breaker (MANUAL.md → *When stuck*) instead of looping. When the circuit-breaker stops the run — here or in step 4 — or a Critical/High stays unresolved, set `Status: blocked — <reason>` in `task.md` (redacted) — with a queue, this halts the whole queue (MANUAL.md → *Scope & the queue*) — and stop and report.

7. **Report, commit & advance.** Summarize: what changed (files), what the reviews found and how you resolved it, the test results, and any accepted Low-severity items. Then, with the gate clean, **commit the change on a work branch** (branch first if you're on the default branch; stage only intended files — see MANUAL.md → *Committing & publishing*). Only after the commit succeeds, update `.agentic/task.md`: check off the deliverable just committed as `- [x] <deliverable> — <sha>` and remove its nested plan steps (a single-deliverable run checks every plan item and adds a `Commit: <sha>` line), so a later stranded-run check or `/cas:resume` can confirm each item against `git log`; the step 4 verify evidence stays at the top level. Then:
   - **Queue empty** — every deliverable's box is checked: set `Status: done`. The run is complete; the report lists every deliverable with its commit, every skipped one with its recorded date and channel, and every kept one with its date and channel and a warning that it never had a confirmed gate pass. Leave pushing / PRs to the user: `/cas:ship` is the curated publish path.
   - **Unstarted items remain** — this is a checkpoint, not a finish (MANUAL.md → *Scope & the queue*). Set `Status: planning` at once, then return to step 1 for the next item — its `cas:planner` dispatch, given the commits since `Base:`, is the reconcile. First check that the next item is one you restated at acceptance (after compaction: one the stored task text names) or one a `Steering:` line from this run added; on a mismatch, stop and go through `/cas:resume`. That re-entry continues an accepted run, so skip the stranded-run check and the initial `task.md` write — but only when the latest SHA-bearing box equals `git rev-parse HEAD` and the worktree is clean; otherwise stop and go through `/cas:resume`. Still run the provenance one-liner, since the commit you just made is the likeliest way `.agentic/` becomes tracked. Edit the live `task.md` in place (redacting per MANUAL.md → *Run artifacts*): nest the next item's plan steps under its box, set `Status:` to the phase the item starts in (`designing` if step 2 applies, else `implementing`), and leave every checked box checked.

   **The queue is the user's.** Never add, remove, or reorder `Accepted scope:` items yourself. When the user changes the queue mid-run (a reply), apply it and record it in a `Steering:` list in `task.md` — `- <date> via reply: <what changed>` (redacted) — so `/cas:resume` can trace the change; a skip is checked as `- [x] <deliverable> — skipped by user (<date>, via reply)`. A skipped in-flight item's uncommitted edits are discarded only with the user's confirmation; if the user keeps them, the queue cannot advance until the tree is clean — tell them so.

Honor the Definition of Done in MANUAL.md. If you cannot meet it, stop and say why.
